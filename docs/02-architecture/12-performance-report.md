## 1. Summary

- At 100k posts / 120k analyses every analytics, mentions and export read path is far inside its NFR (worst p95: overview 30d 474 ms vs 1.5 s; list 120d `count=true` 119 ms vs 1.0 s; detail 4 ms vs 700 ms).
- **No index, view rewrite or migration was added.** Every candidate was measured and none gained more than run-to-run noise (§5). Result numbers are unchanged by construction (no SQL changed).
- One real risk found: with Prisma's prepared-statement cache **on** (direct connection, e.g. local dev or a pooler URL without `pgbouncer=true`), Postgres switches to a generic plan after 5 executions and the same request gets up to **10× slower** (120d list + count 109 → 1104 ms p50, over NFR-002). Production uses `pgbouncer=true`, which disables the cache, so keep it (§4, [env vars](../06-engineering/06-environment-variables.md)).
- NFR-042 aggregate tables are not needed at this volume.

## 3. Method (`perf:explain`)

`pnpm --filter @how-about-me/api perf:explain -- --runs 20 [--out <md>] [--json <path>] [--prepared-cache]` drives the **real** services / repositories (no copied SQL) for 33 scenarios against `PERF_DATABASE_URL`, project `perf-large`, ranges ending at the newest post. Per scenario: 3 warm-up runs, 20 timed runs (wall time incl. Prisma, parallel page + count like `MentionsService.list`, hydration), then every SQL statement the run sent is re-run as `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`. Raw plans go to `--json` (scratch, not committed).

Environment: Apple M1 Pro, 10 cores, 32 GB; PostgreSQL 16.15 in Docker (`shared_buffers` 128 MB, `work_mem` 4 MB, `max_parallel_workers_per_gather` 2); warm cache; single client. The NFRs are defined for staging with k6 at 20 VU — these numbers are a **single-client proxy**, not the acceptance run. Other worktrees shared the Postgres container, so expect ±20 % noise (e.g. `timeseries 48h` p95 121 ms is one outlier, p50 26 ms).

### 4.1 Generic plans with the prepared-statement cache

With the cache on, Prisma reuses one named prepared statement per SQL text and Postgres (`plan_cache_mode = auto`) switches to a generic plan after 5 executions. The mentions page SQL text is the same for every range, so after a few 30-day requests a 120-day request ran the generic plan: **1104 ms p50 / 1580 ms p95** (over NFR-002) vs 109 / 119 ms with custom plans; 30-day non-newest sorts 202–205 ms vs 46–59 ms; most 30-day analytics 2–3× slower. Confirmed by re-running with `ALTER DATABASE … SET plan_cache_mode = force_custom_plan`: 120d 112 ms p50, 30d sorts 45–63 ms. The extra planning cost of custom plans is ~10 ms per statement (newest sort 3 → 12 ms) — acceptable.

Decision: no code change. Production `DATABASE_URL` already carries `?pgbouncer=true` (doc 11 §3, env vars), which makes Prisma skip the statement cache. Any deployment over a direct connection must add `statement_cache_size=0` to `DATABASE_URL` (or set `plan_cache_mode=force_custom_plan` on the role). Local dev and integration tests run with the cache on; that only affects speed, never results.

## 6. Re-running

1. `apps/api/.env`: `PERF_DATABASE_URL=postgresql://…/<name with a perf or test word, e.g. how_about_me_perf>` on localhost (the CLIs refuse anything else without `--allow-any-db`).
2. `DATABASE_URL=$PERF_DATABASE_URL DIRECT_URL=$PERF_DATABASE_URL pnpm --filter @how-about-me/api exec prisma migrate deploy`
3. `pnpm --filter @how-about-me/api perf:seed -- --truncate`
4. `pnpm --filter @how-about-me/api perf:explain -- --runs 20 --out /tmp/perf.md` (add `--prepared-cache` for §4.1).
